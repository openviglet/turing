REST API Reference

Viglet Turing exposes a REST API for integrating search and AI capabilities into any application. All endpoints use JSON. Public endpoints (search, chat, autocomplete) require no authentication. Administrative endpoints require a Key header.

For authentication details, see Authentication. For the interactive API explorer, visit http://localhost:2700/swagger-ui.html.

Authentication

Section titled “Authentication”

Protected endpoints require an API Token in the Key request header:

Create tokens in Administration → API Tokens. See Authentication for step-by-step instructions.

A POST, PUT or DELETE that carries a valid Key needs no CSRF token: the key is what authenticates it, so a server-to-server call has no XSRF-TOKEN cookie to send back. Requests authenticated by a browser session still need one.

Partitioned keys for a shared site

Section titled “Partitioned keys for a shared site”

Several clients can share one SN site, each writing its own documents with a field that tells them apart, for example site_key. Bind each client’s token to its partition: in Administration → API Tokens, set Partition of a shared site to the field and the value (site_key and a.example.org), or send partitionField and partitionValue to /api/dev/token.

The server then confines that key, whatever the request asks for:

Endpoint With a partitioned key
Search: GET/POST /api/sn/{site}/search, /search/query, /search/list, /search/list/query Only the partition’s documents are returned, and facets count only them. The similar-documents widget and duplicate clusters are left out, and the search cache is not used.
/search/locales, /search/sort-options, POST /click As for any key
GET /api/sn/{site}/search/similar, POST /search/similar/query Only the partition’s documents are returned, for a seed document in the partition (another seed answers []). The lexical (MLT) path answers, even on a site whose vector mode would otherwise answer.
GET /api/sn/{site}/search/document Only the partition’s documents are returned, and 404 when none of the ids is in it
GET /api/sn/{site}/ac, POST /ac/query Suggestions are the site’s terms that occur in the partition’s documents, never another partition’s
GET /api/sn/{site}/{locale}/spell-check No correction: the dictionary is built from the whole site
GET /api/sn/{site}/{locale}/related-terms As for any key: the thesaurus is site configuration
GET /api/sn/{siteId}/metrics/failed-searches, /content-gaps, /clicks Read from the partition’s searches and clicks only. The search and click logs record the partition from this release on, so earlier searches are not counted
POST /api/sn/import, /import/bulk Each document gets the partition value stamped on. A CREATE or DELETE whose id already belongs to another partition, or to a document stored without one, is refused with 403, and so is a document that carries a different value. A delete by field gets the partition added, so it stays inside the partition; a delete by type is refused.
GET /api/sn, GET /api/sn/{siteId} Read-only, as for any key: the site’s configuration is shared by every partition. Changing or deleting a site, and the site export, are refused
POST /api/sn/manifest/plan As for any key
POST /api/sn/manifest Answers as for any key when the manifest matches the site as it is, so a connector can re-post it on every run. A manifest that would create the site or change anything on it is refused with 403, because the schema is shared by every partition: provision it with a key without a partition
POST /api/v2/summary Summarises the data you send, and caches the summary apart from every other key’s, so two partitions using the same cacheKey never read each other’s
GET /api/sn/{site}/ai/capabilities, /chat/enabled, /copilot/available, /summary/available As for any key: each answers from the site’s configuration, and none returns a document
/api/sn/{siteId}/spotlight (list, read, create, change, delete) A spotlight created with the key belongs to its partition: it shows only in the partition’s searches, and the key lists, changes and deletes only those. Spotlights made without a partition show in every search, and the key cannot see or change them. A pinned document from another partition is left out of the results
GET /api/sn/{siteId}/synonym, /synonym/{id} As for any key. Changing synonyms is refused with 403, because the site has one set of synonyms that every partition shares
POST /api/sn/{site}/chat/conversation, GET /api/sn/{site}/answer The answer is grounded only in the partition’s documents, and runs without the agent’s tools. Natural-language filters are not extracted from the question. A site whose AI index was built before its documents carried the partition field answers that the index holds nothing for the partition until an administrator reindexes the site’s vectors. A site answered by the catalog assistant (vectorless) refuses the key
POST /api/sn/{site}/nl-filters Each value is checked against the values the partition’s documents hold, so a value only another partition holds is dropped
GET /api/sn/{site}/search/duplicates, POST /search/duplicates/query A seed document outside the partition answers an empty cluster, and only the partition’s documents can join one. A site whose vectors were written before they carried the partition field answers 403 until an administrator reindexes it
POST /api/sn/{site}/copilot, /copilot/kit The catalog assistant answers, and stages kits, from the partition’s documents only. A vectorless site’s chat (/chat/conversation, answered by this assistant) still refuses the key
Every other endpoint, including the other chat endpoints, the DSL _search, ranking expressions and the other tuning APIs, the other metrics, the zip import and MCP Refused with 403 (401 on MCP) until it enforces partitions

A key without a partition, and a browser session, are not affected. A session the key opens keeps its partition, so a client that resends the session cookie without the key is confined the same way, and a request that sends a key is answered as that key even beside another key’s session. The partition field must be a stored field, because the import reads it back from the stored document before it replaces or deletes one.

Section titled “Public Endpoints (no authentication required)”

Certain endpoints are publicly accessible, allowing client applications to perform searches and chat without managing sessions:

Endpoint Purpose
GET /api/sn/*/search Semantic Navigation search
POST /api/sn/*/search/query Semantic Navigation search, JSON body (POST-native search)
POST /api/sn/*/search/list/query Select-list projection, JSON body
GET /api/sn/*/search/similar Documents similar to id, narrowed by fq[], fq.and[], fq.or[], fq.op and fqi.op like a search: fq[]=site_key:a&fq[]=site_key:b&fqi.op=OR returns neighbours from either site

POST /api/sn/*/search/similar/query, POST /api/sn/*/search/duplicates/query The same two calls with a JSON body, answering as the GET does: {"id": "post-7", "rows": 6, "locale": "en_US", "fq": ["site_key:a", "site_key:b", "type:post"], "fqItemOperator": "OR"}. GET /api/sn/*/ac Autocomplete

POST /api/sn/*/nl-filters A visitor’s description as search filters (Natural-language filters)

POST /api/ocr/** OCR text extraction
POST /api/v2/integration/** External integration endpoints
GET /api/v2/guest/status, GET /api/v2/guest/login The read-only guest console: status says whether the host offers it, and login signs the browser in as the guest and opens the console. Off unless the host sets turing.guest-console.enabled=true (local authentication only). The guest browses every screen and saves nothing: every request that would change something answers 403, and so do the users, groups, API tokens, gateway keys and exports

Search

Section titled “Search”

The core search endpoint. Returns results, facets, spotlights, spell-check suggestions, and pagination.

Query Parameters (GET):

Parameter Required Description
q ✅ Search query
_setlocale ✅ Locale code (e.g., en_US, pt_BR)
p Page number (default: 1)
rows Results per page (overrides site default)
sort Sort field and direction (e.g., date desc)
fq[] Filter query: apply a facet filter (e.g., fq[]=type:news). A leading - excludes the value instead: fq[]=site_key:a&fq[]=-source_apps:wordpress answers the documents under a that did not come from WordPress. An exclusion always narrows, whatever fq.op or fqi.op say, also inside fq.or[], and on its own it matches every other document. A Content AI source answers 400, as it cannot exclude
fq.and[] / fq.or[] Filter queries every result must match / of which a result must match one
fq.op How filters on different fields combine: AND, OR or NONE (the site’s setting)
fqi.op How the values of one field combine: AND, OR or NONE. fqi.op=OR with fq[]=site_key:a&fq[]=site_key:b returns both sites’ documents, and applies to every field in the request
group Group results by a field value

Search Response Structure

Section titled “Search Response Structure”

The search response is a self-describing navigational JSON: every link a user might follow (apply a filter, remove a filter, paginate, filter by metadata) is pre-built and ready to use. The front-end does not need to construct query strings or manage filter state.

Top-level sections:

Section Description
pagination Pre-built page links (FIRST, PREVIOUS, CURRENT, NEXT, LAST), the front-end follows them directly
queryContext Result count, page info, response time, active facet operators, and default field mappings
results.document Array of matched documents. Each contains fields (all indexed values), metadata (facet values with pre-built filter links), source, and elevate flag
widget.facet Primary facet groups with counts and pre-built filter/clear links per value. Enabled by Facet = true
widget.secondaryFacet Separate facet groups for fields promoted to Secondary Facet, independent from facet, for different UI treatment (e.g., tabs)
widget.similar More Like This results. Enabled by MLT = true
widget.spellCheck Spelling correction with original, corrected text, and usingCorrectedText flag. Enabled by Spell Check = true
widget.spotlights Curated documents injected at configured positions when the query matches a spotlight term
widget.locales All configured locales with pre-built links: use as valid values for _setlocale
widget.cleanUpFacets Pre-built link to clear all active facet filters
groups Grouped results when the group parameter is used

Self-describing navigation operates at three levels:

  1. Facet navigation: Each facet value carries pre-built links for applying, removing, or clearing filters
  2. Document metadata navigation: Each result’s metadata values carry filter links (e.g., click a type:article tag to filter all articles)
  3. Pagination: Next/previous/specific page links are included; no offset calculation needed

A Turing search UI can be built as a pure rendering layer: render results, facets, tags, pagination, and locale switchers directly from the response. Adding a new facet to the SN Site configuration propagates automatically, with no client code changes.

Locale selection:

Keeping a search out of the metrics: a request sent with an API key or a signed-in session can add populateMetrics=false, so a probe, a test or a monitoring check never shows up in the site’s search insights. An anonymous request is counted whatever it sends, so a visitor cannot hide searches. Autocomplete and the answer stream are never counted as searches.

POST-native search

Section titled “POST-native search”

POST /api/sn/{siteName}/search above is the authenticated endpoint: it accepts the impersonation fields (userId, the conditional targeting maps) and populateMetrics: true, and returns 401 without a principal.

For public, client-side search there is a second, anonymous POST endpoint that takes a clean read-only JSON body:

Use it when a filter value can contain a character that means something in a query string: &, =, +, #, % or a space. A JSON body has no query-string grammar, so a value like section:RAG & Chat cannot be mis-read as query structure. Nothing is deprecated: GET /search and its links stay, and are still the right choice for deep-linkable, bookmarkable, SEO-crawlable and no-JS search pages.

Field Type Description
q (alias query) string Search query (default *)
locale string Locale code, e.g. en_US
page (alias p) integer Page number (default 1)
rows integer Results per page
sort string relevance, newest, oldest or a custom sort name
group string Group results by field
fq / fqAnd / fqOr string[] Filter queries, each a raw field:value
fqOperator / fqItemOperator string Operators between / within facet groups
fieldList (alias fl) string[] Restrict which fields are returned
targetingRules string[] Targeting rules (no conditional maps, read-only)
autoCorrectionDisabled boolean Skip spelling auto-correction (default true)
responseFormat string LINKS (default) or STRUCTURED (see below)
includeSortOptions boolean false. When true, a STRUCTURED response also carries sortOptions
mode string standard (default) or instant. Send instant from a search box that updates while the visitor types: the last term of q matches as a prefix (work finds “Workshop”), and the query is not recorded in the search metrics. A query that already uses syntax (a phrase, field:value, a wildcard, AND/OR/NOT) and a last term shorter than 2 characters run as typed. request.q echoes what was typed
populateMetrics boolean true. Send false to keep a provisional search out of the search metrics while it still runs exactly as typed, for example a first search your client refines right after. Only false has an effect (true does not record an instant search), and the echoed request never carries false, so the refined search built from it is recorded

The endpoint is anonymous and CSRF-exempt, so a browser client needs no /csrf priming round-trip.

The STRUCTURED response

Section titled “The STRUCTURED response”

responseFormat: "LINKS" (the default) returns the same link-bearing body as the GET endpoint, so a client can move to POST without changing how it reads the response.

responseFormat: "STRUCTURED" returns a link-free body instead. The contract is: take the echoed request, apply one structured change, send it back.

A few fields carry state rather than navigation, and are present only when the site or the request produced them:

Field When it appears
icon the site configured an icon. A plain Iconify name (tabler:building-store). Render it as the search header’s brand mark, falling back to your own logo when absent
similar the request named a seed document: the “more like this” neighbours, each { id, title, type, url }
spotlights the site pinned documents for this query: each { id, position, title, type, referenceId, content, link }, position being the 1-based slot to inject it at
sortOptions the request asked for includeSortOptions (see below)

url and link above are the documents’ own destinations, the same kind of value results[].fields.url carries, not search actions. Every navigation that used to be a URL is a value to put on the next request:

Instead of following… Do this
a facet item’s link apply item.action (ADD / REMOVE / REPLACE) to request.fq using item.filterQuery
a document’s metadata[].href apply the chip’s own action to request.fq using its filterQuery, exactly as for a facet item, because it is the same action (chips are {field, value, filterQuery, text, selected, action} here)
a facet’s cleanUpLink remove facet.clearFilterQueries from request.fq
the widget’s cleanUpFacets clear request.fq (see selectedFilterQueries)
a pagination href set request.page = page.page
a locale link set request.locale
a spell-check link set request.q = spellCheck.correctedTextValue

An applied facet stays in facets whatever the site’s facet item type. Its selected value has selected: true and the facet’s clearFilterQueries names what to remove. The LINKS response keeps the older behaviour, where a site whose item type is not OR drops an applied facet and lists it under widget.facetToRemove.

Both JavaScript SDKs do this for you: see @viglet/turing-sdk (toggleFacet, clearFacet, clearAllFilters, goToPage, applySpellCheck) and @viglet/turing-react-sdk.

Sort options in one round-trip

Section titled “Sort options in one round-trip”

The sort option list has its own endpoint (GET /api/sn/{siteName}/search/sort-options) and is not part of the response by default: the control is already rendered on every request after the first. To paint it on the first frame without a second call, ask for it:

The response then carries a sortOptions array of { "value", "label" }, exactly what the dedicated endpoint serves. Put the chosen value on request.sort.

The flag is not echoed back on request, so re-sending the echoed object asks for results without re-fetching the list. It has no effect on a LINKS response.

responseFormat on GET

Section titled “responseFormat on GET”

responseFormat is a plain request field, not an Accept header, so the GET search endpoint honours it too, handy for comparing the two shapes against one query, or for a server-rendered page that wants facet data without parsing links:

The value is case-insensitive (structured works). Omitting it returns the regular link-bearing response, unchanged; an unrecognised value returns 400 Bad Request rather than silently falling back.

Natural-language filters

Section titled “Natural-language filters”

Turns a visitor’s description into the q and fq of the site’s own search, so a page can show the ranked, faceted results for “part-time job near the subway in Sao Paulo” instead of a chat answer.

Body field Required Description
text ✅ The visitor’s request
locale Search locale; when left out, the site’s first locale
filters Field to accepted values, for example {"site_key": ["a"]}: each value is checked only against the values these documents hold

Example:

Pass q and fq to the search (POST /api/sn/{site}/search/query) as they are. Turing checks every value against the values the site actually holds and spells it the way the site indexes it (sao paulo becomes São Paulo). A value the site does not hold is left out of fq and listed in dropped with the reason (NOT_IN_SITE, or UNKNOWN_FIELD for a field the site does not have).

Relative dates are resolved against the server’s date, in English and Portuguese: “last year”, “this month”, “last month”, “the last 7 days”, “since March”, “since 2024” (“ano passado”, “neste mês”, “desde março”, …). “Last year” asked on 2026-10-24 becomes [2025-01-01 TO 2025-12-31]. A date range the text neither phrases that way nor dates with a year is a guess, so it is left out of fq and listed in dropped as UNGROUNDED_DATE.

Response field Meaning
q What is left to match as free text
fq field:value per value and field:[start TO end] per range, the form the search takes
filters[].sourceWords The words of the request each value was read from. For a range, the whole span: the bound phrase, the currency and the amount as the request formats it (under $400, até R$ 2.200, from 2024), and one span when both ends are named (between $100 and $200). Each span leaves q at its own position, so an amount repeated elsewhere in the request stays
filters[].confidence 1 when the request spells the value, 0.6 when it was inferred (a synonym, a translation), 0.3 when the engine could not list the field’s values to check it
available false when no LLM is configured: nothing is filtered and q is the whole request

The call spends one LLM completion, so it is gated like the site chat: a site in API-key mode requires its key, and anonymous calls share the chat’s rate limit. From the SDKs, call postNlFilters (JavaScript SDK).

The site chat and the catalog copilot read list-style questions (“quais vagas em São Paulo?”) through the same extraction, so their answers are narrowed by the same checked values. To receive those filters in the chat stream, send "includeFilters": true in the body of POST /api/sn/{siteName}/chat/conversation: a list-style question then streams one filters event, carrying the same JSON as above, before the answer. It is off by default, because a client that predates the event would show it as answer text.

Asking about one document. POST /api/sn/{site}/chat/conversation and POST /api/sn/{site}/copilot both take an optional documentId, the indexed id of the document the question is about (the product on the page). That document leads the answer’s context and is always among its sources; whatever the question retrieves stays in the context, as alternatives the answer names as such. It is never a filter, and an id the site does not hold is ignored. From the SDKs, pass documentId in the chat options, or in the request of postCopilot.

One site of a shared SN site. When several sites index into one SN site, each document carries a field that names its site (for example site_key). POST /api/sn/{site}/copilot, POST /api/sn/{site}/copilot/kit and POST /api/sn/{site}/nl-filters take an optional filters body field, field to accepted values ({"site_key": ["a"]}, the same shape the chat’s filters takes). Every read the call makes stays inside it: the documents the copilot cites and the kit stages, a pinned documentId, the hybrid reorder, and the values nl-filters checks against. Values of one field are alternatives, and all named fields must match. A call with no filters reads the whole site, as before. This narrows what an anonymous browser sees; it is not access control, which is what a partitioned API key gives a server. From the SDKs, pass filters in the request of postCopilot and postCopilotKit, or in the options of postNlFilters.

Deep-dive research

Section titled “Deep-dive research”

A question whose answer is spread over many documents (“what has the school done on public health?”) gets a sectioned overview instead of one paragraph. Turing plans 3 to 6 sub-questions, searches the site for each, and writes one section per sub-question the documents answer, each claim citing the source it comes from as [n].

Field Description
question The question to research (required)
locale The language of the overview; a locale the site has no index for falls back to its default indexed one
filters Field to accepted values, e.g. {"site_key": ["main"]}. Every search the research makes stays inside them
maxSteps How many sub-questions to plan, 3 to 6 (default 5)

The response is a stream of named Server-Sent Events, in this order:

Event Data
plan summary (the question restated) and steps (index, question, query)
step One per sub-question once searched: hits (0 when the site has nothing on it), the source numbers it brought, and widenedBy (field=value) when a thin search was retried inside the facet value its words name
section title, text with [n] citations, and citations (the numbers the text cites)
uncovered items: the sub-questions and topics the documents do not answer. They are reported, never filled from general knowledge
timeline entries (date, title, url, source), oldest first: the cited documents that carry a date, read from a field named like one (eventEnd, publicationDate, dataInicio). Sent only when at least two cited documents are dated
sources groups: the cited documents by their type (other when a document has none), each with the rank the sections cite
done The number of sections and sources
error message, when the research is refused or fails; it ends the stream

Every section cites at least one listed document: a section the model wrote without one is dropped and named in uncovered, and a citation to a number no source has is removed. When no sub-question finds anything, the stream ends with error instead of an overview.

The research needs the same as the answer stream: AI enabled on the site and a default LLM. It is metered as the sn.research stage, so it shows in the site’s cost summary and counts against the site agent’s monthly budget, and it is rate-limited like chat for anonymous callers. A partitioned API key is refused.

AI capabilities of a site

Section titled “AI capabilities of a site”

Which AI features a site can use, read from its configuration. No model is called, so a page can ask before it shows an AI block. It needs no login; a site in API_KEY mode needs its key, as for search.

chat and answer always agree, and carry the same reason as GET /api/sn/{siteName}/chat/enabled (NO_GENAI, NO_AGENT, RAG_DISABLED, MISSING_EMBEDDING, …). The features that only need a default LLM report MISSING_DEFAULT_LLM when none is set.

similarByVector is the one answer that looks past configuration: when the site is set up for RAG but its vector store holds none of its content, it reports NOT_EMBEDDED. That happens when the content was indexed before generative AI was turned on; reindex the site to fix it. Chat stays enabled meanwhile, but it will not find the content. The check lists one stored chunk per locale, never calls a model, and is cached for a minute; a store that cannot list chunks reports the site as ready. From @viglet/turing-sdk: fetchAiCapabilities(client, site).

Search Insights API

Section titled “Search Insights API”

What visitors searched for and did not find. Both endpoints take the site’s id and the same window, and need authentication (a Key header or a session).

Parameter Meaning
from, to ISO-8601 instants. to defaults to now; without from the report covers all time
period Shorthand for from: today, this-week, this-month or all-time
rows How many terms, 1 to 50 (default 10)

failed-searches lists the queries that returned nothing every time they ran. content-gaps lists the queries searched often whose average result count is under 3: what to write next. Both answer { from, to, terms: [{ term, searches, avgResults, lastSeen }], metricsEnabled }, most searched first; terms searched equally often come back most recently searched first, so a new gap is not cut off by older ones. These are the same reports the MCP tools top_failed_searches and content_gaps read.

Searches are counted together when they differ only by case, spacing or accents (emergência and emergencia are one term), and each term is shown in the spelling visitors typed most, accents included. Letters are never dropped, so a search in Cyrillic, Greek, Arabic or Japanese is listed as typed. Searches logged before this release still group by the older key, which deleted every letter outside basic Latin.

metricsEnabled is false when the server does not record searches (turing.search.metrics.enabled is off). An empty report then says nothing about the site’s traffic, so show the user that metrics are off rather than an empty list.

From @viglet/turing-sdk: fetchFailedSearches(client, siteId, { period: "this-month" }) and fetchContentGaps(...), with a client created with an apiKey.

Click-through rates

Section titled “Click-through rates”

The clicks your search page reports to POST /api/sn/{site}/click are read back here. The window and authentication are the same as above, plus an optional locale (pt_BR or pt-BR) that narrows both the searches and the clicks to one locale.

ctr is clicks per search, so it can pass 1 when visitors open several results. terms are the most searched terms first. neverClicked lists terms that found results nobody opened: a relevance problem, unlike failed-searches, which is a content problem. The console’s Top search terms page shows the same numbers as a click-through column.

Clicks are recorded only when turing.search.metrics.enabled is on (env TURING_SEARCH_METRICS_ENABLED=true). When it is off, POST /click drops the click and answers 204 with the header X-Turing-Metrics: disabled, so a client can tell why nothing is counted. When it is on, the answer is 202. The reports say the same in their body: metricsEnabled on clicks, failed-searches and content-gaps.

From the vanilla SDK: fetchClickThrough(client, siteId, { period: "this-month", locale: "pt-BR" }).

Clearing a site’s metrics

Section titled “Clearing a site’s metrics”

Probes, tests and evaluation runs are logged like any visitor’s search, so before a demo they can fill the insights above. Clear them:

It removes the site’s recorded searches and clicks, all of them, or with before (an ISO-8601 instant) only those recorded earlier. The answer says how many went: { "searches": 412, "clicks": 37 }. It needs authentication, a key bound to a partition is refused, and every clear is logged with the user who made it. It cannot be undone.

In the console, the Top search terms page has a Clear metrics button beside the period picker, which asks before clearing.
